## 一、环境与部署(新设备装机)

### T1 .env 整份跨机拷贝 → 数据落盘 PermissionError

**现象**:新 UOS 设备上任何写数据操作(建索引/记忆)抛
`PermissionError: [Errno 13] Permission denied: '/home/tnc/.local/share/rootrecall/...'` —— 那是**旧机的家目录**,新机上不存在且无权限。

**根因**:`.env` 是机器相关的:quickstart 按本机写入 `ROOTRECALL_HOME` 等路径变量。为了省事把旧机 `.env` 整份 scp 到新机,`load_dotenv` 之后 `data_root()`(src/rootrecall/services/repos/registry.py:45)指向旧机路径,所有落盘全炸。

**修复**(三层):
1. 治标:新机删掉 `.env` 里的 `ROOTRECALL_HOME` 行,数据回落安装根;
2. 治本:CLI 入口加 OSError 守卫(src/rootrecall/cli.py:950)—— `e.filename` 与 `ROOTRECALL_HOME` 前缀互含 → 打友好提示(指向 .env 疑点)+ rc=1,不再甩 traceback;
3. 防再犯:`.env.example` 头部加警告「换新设备只把 key 值抄过去,别整份拷」。

**预防**:回归测试 `tests/e2e/test_baseline_add_e2e.py::test_stale_rootrecall_home_friendly_error`(阻断文件充当 HOME 父目录 → 断言 rc=1、提示含「ROOTRECALL_HOME」、无 Traceback)。

**教训**:机器相关配置(路径)与密钥(可拷)必须分离对待;凡 env 驱动路径,入口处校验「可写」再干活,别让深层第一次写文件时才炸。

### T3 github 拉取间歇卡死 → git bundle 内网同步

**现象**:测试机上 `git pull` github 仓库间歇性无限挂死 —— 浏览器访问 github 网页正常、release/对象 CDN 拉取卡住,`git pull` 两次卡死两次。

**根因**:测试机网络对 github CDN 不稳定(网页可达 ≠ git 对象可达)。

**绕法**(已成固定套路):本地打包增量 bundle → scp 过去 → 远端从 bundle 拉:
```bash
git bundle create /tmp/rr.bundle <prev>..main      # 本地
scp /tmp/rr.bundle uos@<测试机>:/tmp/               # 内网,稳定
git -C ~/Desktop/RootRecall pull /tmp/rr.bundle main   # 远端
```

**教训**:内网双机同步别死磕公网 CDN;git bundle 零依赖、增量小,是 LAN 环境最可靠的代码同步通道。同场加映:远端装大件(opencode 二进制)也走 scp,不走 curl 直链。

### T4 /usr/local 只读 → opencode 安装位与「打不开」

**现象**:① UOS 25 的 `/usr/local/bin` 在**只读文件系统**上,`ln -s` 静默失败,opencode 无法软链进系统 PATH;② 装好后用户反馈「opencode 打不开」。

**根因**:① 发行版把 /usr/local 挂只读,写入静默失败(`ln -s` 不带 -f 时返回成功假象);② 「打不开」实为新 shell 未加载 PATH —— 二进制放进 `~/.local/bin` 后只在 `.bashrc` 里加了 PATH,当时会话没重开。

**绕法**:二进制直接落 `~/.local/bin/` + `.bashrc` 追加 `export PATH="$HOME/.local/bin:$PATH"`,**开新终端**验证 `opencode --version`。

**教训**:往系统位置装东西前先探测挂载(`findmnt <目录>` 看 ro/rw);装完的验证必须在**新 shell** 里做 —— PATH 改动对当前会话不生效,「装好了但打不开」九成是这。

## 二、外部 API

### T2 DashScope embedding 超长输入 400 —— 上限是 token,不是字符

**现象**:新机 `baseline add` 建索引进度推到 embedding 阶段整体失败,DashScope 返回
`400 Bad Request: Range of input length should be [1, 8192]`,大文件仓(bluez)全军覆没,索引建不出来。

**根因**(两层,第二层是重点):
1. `RemoteEmbedder.embed_chunks` 没有 input 长度守卫,密代码单 chunk 轻松超限;
2. **第一次修复就踩了第二层坑**:按报错字面把 8192 当字符、放了个 24000 字符的预算 —— 仍然 400。报错里的 range 单位是 **token**(text-embedding-v4 单输入上限 8192 token),密代码 token 密度 ~1.3–1.5 token/字符。实证探测:12000 字符过、16000 字符死。

**修复**(commit 70e62ff,src/rootrecall/services/code_index/embed.py:80):
- `DEFAULT_MAX_INPUT_CHARS = 8000` —— 按**最坏 token 密度**定的字符预算(任何密度下都 <8192 token);
- 只截断**送嵌的文本**:存库全文、BM25/fts 不受影响(截断只为过 API,不为省存储);
- 预算进模型指纹(`…|tc{N}`,embed.py:208)—— 改预算会使旧指纹失效触发全量重嵌,这是**有意的**(不同预算的向量不该混在一张表里),别当 bug 修;
- 配置键 `code_index.embedding.max_input_chars`,0 = 关闭守卫。

**预防**:`tests/test_embed.py::test_remote_embedder_truncates_oversized_input`(fake client 断言送嵌长度 ≤ 预算、chunk 原文未动、指纹含 tc100)。

**教训**:① 报错里的数值先核**单位**(token ≠ 字符),再定防线;② 防线预算按最坏密度留余量,别贴着报错数字修;③ 上限类问题用**实证探测**(二分几个真实样本)优于读文档猜 —— 文档常常不写单位。

## 三、agent 行为(真实测试报告分析)

### T5 BASS UUID 半幻觉 —— 标准值与归因双错,验收没拦住

**现象**:真机测试报告(`data/bug_rca/bluez-rca.md`)「关键发现」称:v25 的 BASS 服务 UUID `0x184F` 与「官方标准 `0x185F`」不符、判定为 **fork 偏差**。逐层核查后**双重错误**:
1. **归因错**:upstream bluez 5.87 `bass.c:57` 同样定义 `"0000184f-…"` —— 这不是 fork 偏差,上游原样;
2. **标准值错**:Bluetooth SIG Assigned Numbers 官方 BASS = **0x184F**;0x185F 是 Generic Voice Assistant Service —— 报告里的「官方值」是模型凭训练记忆编的。

**根因**:防幻觉验收只核 **file:line**(代码层为真 ✓),但 file:line 只证「代码里确实这么写」,**证不了「标准要求什么」**,也证不了「差异是谁改的」。标准值断言与 fork 归因断言是两种不同事实类型,没有各自的核验关卡 —— 混过去就成了「半幻觉」(代码引用全真、结论全错)。

**修复**(🔧 本批):给产报告的三条工作流补硬纪律 ——
- `.claude/skills/bug-rca/SKILL.md` 硬约束 +2 条:标准值断言必须带**规范原文 source_url**(抓不到就降级写「标准值未核」);归因断言(「fork 改的/上游本来就这样」)必须先对照 **upstream 基线**同位置;
- `onboarding` / `compare` SKILL.md 同款(compare 措辞是「三源归因」:v20/v25 差异要说谁改的,必须对照 upstream 第三源);
- 8 个 subagent 提示词与 SKILL.md 是**各自独立维护**的(不吃软链)—— `config/opencode_rootrecall.json` 里 rootrecall-bug-rca / compare / onboarding 三个的 prompt 定点插入同款纪律。

**预防**:纪律级(prompt),暂无自动硬门;验收清单要加一栏「标准值/归因类断言 → 有无 source_url / 有无 upstream 对照」。

**教训**:① 验收核验维度要覆盖**结论的事实类型** —— 代码事实(file:line)、标准事实(source_url)、归因事实(双仓对照)各要各的证据;② 训练记忆里的标准号/UUID/常量是幻觉高发区,「记得官方是 X」一律当作待证假设。

### T6 codebase 双命名 → 连败 4 次浪费调用

**现象**:实测中 agent 从记忆召回拿到**项目名** `bluez`(记忆 scope 的设计:教训跨版本共享),传给图/索引工具(要**注册名** `bluez-v25`)—— 连续 4 次失败才试对名字;更糟的是旧报错还**误导**:`代码库 'bluez' 还没建索引,先建:uv run rootrecall index <路径> bluez` —— 引导 agent 去建一个平行索引而不是换名字。

**根因**:同一实体两套命名(记忆=项目名 / 索引·图=注册名)都是**有意设计**,但工具层对未知名字零容错、报错不列候选,agent 只能盲试。

**修复**(🔧 本批,src/rootrecall/tools/mcp_memory.py:92/113 + src/rootrecall/services/repos/registry.py:283):
- `known_codebases()`:注册表 ∪ 索引清单(`index_manifest.json` marker)∪ 结构图目录(`graph.db` marker)三源并集,半成品不算数、坏源跳过;
- 工具层三级解析(**精确 > 归一化**(`bluez_v25`↔`bluez-v25`,大小写/斜杠)**> 唯一子串**,子串双向):唯一命中**自动纠偏**且输出头注明(`codebase 'bluez' 近义解析为 'bluez-v25'`);多候选列出全部 + 指路 `baseline ls`;完全未知名列本机已知清单;
- 报错区分「**在册但没建图/索引**」(指路 `rootrecall index` 重建)vs「**完全未知**」(指路 `baseline add`);
- 七个索引/图工具接线;记忆三件套**故意不接**(scope 吃项目名是既有语义,容错反而会串版本线)。

**预防**:`tests/test_codebase_fuzzy.py` 17 条(纯函数分档 / 三源收集含坏源容错 / 解析分支 / build_server 工具级接线)。

**教训**:① 同一实体多套命名是正常设计,但**工具边界必须做近义容错 + 候选提示**,报错的目标是让调用方**一次改对**;② 报错文案别急着教人「去建 X」—— 先确认 X 是不是本来就该以别的名字存在。

### T7 CodeGraph 默认 base_dir 与建图落点分裂(潜伏,修 T6 时挖出)

**现象**:无直接症状 —— 实现 T6 时核对路径发现:`CodeGraph.build/update/open` 的默认 `base_dir="data/structgraph"` 是 **cwd 相对**,而 CLI 建图传的是 **reanchor 路径**(src/rootrecall/cli.py:88/124)。`ROOTRECALL_HOME` 设置的机器上,图建到 `$HOME/structgraph/`,工具却去 cwd 找 → 图建成后所有图类工具 FileNotFoundError。

### T11 domain_knowledge 裂池:同主题一条记 bluez、一条记 general,recall 查一个漏一个

**现象**(三份报告合力还原,2026-08-26):test2 会话把 A2DP 知识记进 `general`(id=e96d2ac5,纯网调简介版);test 会话把 A2DP 知识记进 `bluez`(id=aecae974,带源码交叉验证的详细版)。demo 目录的第三个会话问「A2DP」,recall 只查 general 只见一条 —— 用户预期两条,排查花了 5 次 recall + dump + 甚至翻 opencode 会话库才定位:不是记忆丢了,是**裂在两个池子**。

**根因**:记忆按 (owner, codebase) 作用域硬隔离本身是对的(项目事实不串库),但 domain_knowledge 是**跨项目通用知识**;domain-research 菜谱里「codebase=<绑哪个仓或 general>」的两可措辞,让两个会话各自选了不同池 —— 写侧不归一、读侧单池查,裂池必然发生。

**修复**(🔧 本批,读写两侧一起堵):
- **写侧归一**:`memory_memorize(kind=domain_knowledge)` 无视传参**强制落 general 池**,输出注明原传值(src/rootrecall/tools/mcp_memory.py);
- **读侧并查**:`memory_recall` 总是**并查 general 池**(active ∪ general,按 item_id 去重、跨池条目前缀 `[general]` 亮明住处);
- 菜谱对齐:domain-research SKILL 删掉两可措辞 → 「codebase 不用传,一律 general,关联仓写 summary/tags」。

**预防**:`test_memory_recall_union_general_pool` + `test_memory_memorize_domain_knowledge_forced_general`。

**存量数据**:历史裂池条目(如 aecae974 在 bluez)不自动迁;并查已保证任何会话看得见 general 池全量,bluez 会话还能看到自己池里的旧条。要彻底合并见文末维护说明的迁移 SQL(先 SELECT 核对再 UPDATE)。

**教训**:① 按作用域隔离的存储里,**通用类内容必须有唯一的家**(写侧强制)—— 否则每个会话按当时代码库上下文随手一记就裂池;② 隔离设计与共享需求冲突时读写两侧都要动:只改读侧治不了新裂池,只改写侧治不了存量。

### T12 export_report 固定文件名:同仓多主题报告互相覆盖

- compare SKILL 硬约束加战术条:「search 命中全是外围就转 grep 已知命名模式锚定 src/ 核心文件,搜索留着探索未知模块用」。

**预防**:`test_testinfra_prior_buckets` + `test_testinfra_prior_demotes_peripheral_in_retrieve`。开发中自家反例测试还抓了裸 `endswith("test")` 的假阳性(latest/**greatest**.c 被误降)→ 收紧为显式分隔符形态。

**教训**:① 检索先验的维度要对齐真实噪声形态 —— 这次噪声不是「符号粒度」是「路径属性」;② 先验要软乘不剔除,保住「专门查测试代码」的合法场景;③ 词缀类匹配先写反例(latest/greatest),子串误伤是这类先验的头号坑。

### T14 recall 默认作用域是空池,agent 盲试多轮才发现传错 codebase

**现象**(rootrecall-a2dp-memory-analysis.md 阶段 1/2):同一会话两次不传 `codebase` 的 recall 全空 —— 默认作用域是服务器安装根目录名(永远为空的池);agent 靠逐个试(bluez / general / 默认)拼全貌,3+ 次浪费调用。

**根因**:MCP server 默认 codebase 解析链末位是**进程 cwd 目录名**,opencode 拉起时落到安装根名;空结果又不给「哪些池非空」的提示。

**修复**(🔧 本批):空结果时列出**非空作用域清单**(`store.list_scopes()` + service 透传 + 工具渲染,如 `非空作用域:bluez(6)、general(1)`)+ T11 的并查 general 双保险。

**预防**:`test_memory_recall_miss_lists_scopes`。

**教训**:① 作用域/命名空间型参数,空结果报错要回答「哪些池子非空」—— 让调用方一次改对;② 默认值落在永远为空的池子上 = 默认值设计错误,至少要在空结果里自我暴露。

## 四、测试工程

### T8 argparse help=SUPPRESS 在 py3.12 打印 ==SUPPRESS==

**现象**:baseline 命令族用 `help=argparse.SUPPRESS` 隐藏进阶子命令,`--help` 输出出现字面 `==SUPPRESS==`,且 usage 行仍列出全部子命令 —— 隐藏完全失效还污染帮助。

**根因**:py3.12 对 subparsers 的 `help=SUPPRESS` 处理不完整(渲染层不认)。

**修复**(commit 7274660,src/rootrecall/cli.py):手工过滤 `sub._choices_actions`(只留可见集)+ 显式 `metavar="{baseline,install,here}"`。

**教训**:标准库的「隐藏」类特性跨小版本行为要实测,别假设语义稳定;绕法落在自己代码里要加注释说明针对的版本行为。

### T9 测试断言与用户可见文案耦合,改命令名碎一串

**现象**:CLI 瘦身把 `repo checkout` 改名 `baseline checkout`、`repo register --role baseline` 换成 `baseline add` 后,三个不相干测试文件里的字符串断言(`assert "repo checkout" in out` 之类)接连报红。

**根因**:断言钉在**完整用户可见文案**上,而非关键语义词;文案即接口,改名即破测。

**修复**:更新断言到新命令名;属机械跟进,无代码缺陷。但反向启示成立:文案改动要 grep 测试目录同步,别只跑相关文件。

**教训**:① 用户可见文案 = 接口,改它要全仓 grep 断言;② 断言尽量钉**语义关键词**(命令名、错误码)而非整句,给文案润色留余地。本次 T6/T7 改了报错文案,同步更新了 6 个旧测试的关键词元组并给 fake 图 lambda 加 `**kw` —— 同一条教训的正面示范。

### T10 长任务运维三则(操作纪律)

| 症状 | 纪律 |
|---|---|
| 工具层 `sleep >120s` 两条都被静默中止 | 长等待放进 python(`time.sleep`)或显式传 timeout 参数,别裸 sleep |
| 远端全量建索引一跑几十分钟,阻塞会话 | `nohup … > /tmp/xx.log 2>&1 &` 后台跑 + 轮询 watcher 看日志尾,别前台死等 |
| 测试断言只捕 stdout,错误却打在 stderr | 测试 helper(`_run()`)一开始就同时捕两个流,别等第一例 stderr 报错再改 |
| 测试机 SSH 要交互输密码 | `uv run --no-project --with pexpect python` + `expect(['[Pp]assword:', EOF])` 模式;凭据经 stdin 传,不进命令行/日志 |

**教训**:这几条各自很小,但都在真机测试的关键路径上浪费过整段时间;长任务的「跑法」和「验证法」要先于任务本身定型。
