## 一、LLM 行为与验证边界

### 故事 1:模型连续三次把根因判成「最响的那行日志」(原坑 #11)

**30 秒版**:同一个带金标准的 bug,agent 连续三次 e2e 都把根因判成日志里最显眼的 ERROR 行,补丁能 apply、四道自动验证全绿 —— 但根因是错的,真因在更早 7 秒的一条安静 INFO 日志里。这逼着我们重新设计了整个验证边界。

**背景**:bug-RCA 的金标准案例是 wpa_supplicant 的 P2P 扫描孤儿泄漏:并发 D-Bus 请求覆写了回调指针,扫描完成事件被误路由,孤儿 radio work 没人释放。金标准补丁在误路由点释放。

**排查(三次反转)**:
1. 三轮独立 e2e(pivot 轮 / 老 orchestrator / 新工具链)全部误诊为同一个错误落点:「StopFind 的 abort 失败分支没释放」。拿金标一对才发现**因果时序是倒置的** —— 孤儿在 10:12:12(误路由)就形成了,abort 失败 10:12:19 才发生;`-ENOENT` 是"扫描早已完成但状态没清"的**症状**,不是原因。模型抓 ERROR 级显眼行当下手点,真因那条 `Scan-only results received` 是 INFO 级,安静。
2. 更深的机制是**确认偏差**——锚定假设后,agent 切日志窗从 abort 时刻切(漏掉 7 秒前起点)、grep 全用假设词(abort/ENOENT),从不主动搜反证词。中立工具被假设驱动后,成了确认偏差放大器。
3. 第四轮我们加 prompt 级时序证伪指令 —— 模型照做了,但**问错了问题**(验了一个 trivially 成立的时序);甚至 recall 出"此 bug 会误诊成 abort-fail"的记忆警告,模型用一条错误的事实判断把警告"证伪"了。**prompt 层对系统性偏差不奏效**。第五轮把切窗起点提前 19 秒 —— 模型看到误路由起点,落点与金标三个文件逐行一致。

**根因**:LLM 的注意力会被显眼日志行劫持 + 确认偏差贯穿取证;而验证门只查 apply、不查根因正确性 —— 这是最大盲区。

**解法与结果**:结构性手段替代 prompt:重心转向确定性更高的代码情报(检索/调用链)、多假设清单强制并行展开、定稿前用问题摘要做定向记忆复核、SKILL 教"从更早切 + 主动 grep 反证词"。期间三轮"确定性日志切片工具"尝试(prepend / 扩窗 / 自动摘要)全被 A/B 探针证伪撤销 —— 混合服务日志的信噪比,确定性程序框不住。

**可迁移**:① apply 通过 ≠ 根因对,验证体系必须显式声明"验不了什么";② 同一 bug 反复同向误诊 = 模型系统性偏差,别当偶然,要当流程有盲区;③ 对抗确认偏差要靠确定性手段,soft prompt 会被"在错误假设内自洽"地满足;④ 先验知识(记忆警告)会被模型当待证伪假设反噬,记忆不是万能药。

### 故事 2:「apply 过」不等于「修对了」—— 把验证边界写进产品(原坑 #12)

**30 秒版**:我们把 bug-RCA 从"单 session 九步流水线、一次走完、四道硬门"推翻成"工具箱 + 人在环",并立了一条产品级铁律:自动验证封顶在 apply,编译测试复现永不做 —— 因为系统软件没有可信的本地 oracle。

**穿帮过程**:原设计隐含两个假设:"补丁一次到位"和"apply 过即修对"。e2e 连续打脸:补丁 plausible 但非金标(正是故事 1 的误诊);而 METR 的数据是测试通过的 PR 约一半没被合入 —— 有测试尚且如此,系统软件连单测都没有,本地试编译更不可信(基线本身就编不过:缺 git 标签、缺依赖,`builds=no` 根本归因不了补丁,原坑 #14)。更糟的是老流程在未验证时就 memorize —— 把没坐实的结论写进记忆库,是给未来所有会话埋雷。

**解法**:skill 改工具箱 + 人在环(去固定顺序);memorize / 导报告降为**真机验证通过后的收尾**;correctness 措辞只报推理结论、永不标 tested/verified。编译、复现全归真机上的工程师 —— 不是做不到,是信号歧义,做了反而误导。

**可迁移**:① 根因定位本质是"假设↔证伪"迭代,不是一次走完的流水线;② 未经验证就写入知识库 = 污染未来的自己;③ 自动化验证的价值上限由"它验不了什么"决定,这条边界要显式声明给用户。

### 故事 3:检索命中了,agent 却不「抄答案」—— 42 次工具调用降到 4 次(原坑 #18)

**30 秒版**:记忆系统召回层工作完美 —— 第一步就命中完整的历史调研事实,agent 却当"参考资料",老老实实把七步流程重跑一遍:42 次工具调用、22 次读文件、4 分钟。改一行流程设计(命中即短路)后:4 次调用、40 秒,质量不降。

**背景**:compare skill 的价值主张是"首次调研读码即记,下次 recall 命中秒答"。冷路径(首次)全绿,我们去做热路径 e2e —— 记忆里已有同主题完整对比事实。

**现象与排查**:recall 第一步就命中(两个 codebase 各召回 1245 / 894 字符的完整对比事实),agent 仍整轮重跑,还重复 memorize 两条。它的自述一针见血:**"记忆已命中,但按 skill 流程我需要重新验证"** —— agent 没有错,它忠实执行了一个设计错的流程:SKILL 写成了固定七步 playbook,没有告诉它"什么时候可以不走完"。

**根因**:召回层和注入层是两层。召回层负责把记忆找出来,注入层(SKILL/prompt)决定 agent 怎么消费召回结果 —— 只建召回、不写"命中怎么办",记忆就是被召回然后被浪费。

**解法与结果**:SKILL 与 agent prompt 显式加「recall 优先 + 命中短路」:命中同 codebase 同主题的完整事实 → 直接复用出报告,不 search / read / memorize;短路路径不重复 memorize。实测 42→4 次工具、read 22→0、~4min→~40s(约 7×),报告的关键内容(入口配对表、差异面、双源 file:line)全在。

**可迁移**:① 记忆系统要分层验收:召回命中 ≠ 会被消费,"下次秒答"这类卖点必须**热路径** e2e 验证,冷路径只证明"能记";② skill 是工具箱 + 条件分支,不是必走完的流水线 —— 要显式写出"什么时候可以不走完"。

### 故事 4:工具静默截断 = 对 agent 撒谎(原坑 #19)

**30 秒版**:记忆体检的 e2e 里,agent 反复调用 recall 13 次"补捞"数据 —— 排查发现是全量导出工具做了 8000 字符静默截断:48 条记忆只显示了 24 条,零提示。agent 不知道自己缺数据,只能觉得"数据不对劲"。改成按条目分页 + 显式翻页提示后,一轮拿全。

**排查**:初判"agent 行为异常",核工具实际返回才发现一半条目被吞。两个设计错误叠加:① 截断用**字符数**而非**条目数**,对逻辑单元完整性是盲的;② 截断后**没有任何信号** —— "还有更多"这个事实被吞掉了,agent 基于"所见即全部"的假象做决策,体检结论会漏掉恰恰最该发现的矛盾项。

**解法与结果**:`limit/offset` 按条目分页(默认 60/页)+ header 显式「showing 1-60 of N, more → memory_dump(offset=60)」。把"还有更多"做成诚实信号,agent 知道怎么拿完;e2e 一轮 dump 拿全 48 条,补捞消失。

**可迁移**:① 工具输出截断必须配诚实信号(截了多少 + 怎么拿剩下的),静默截断等于对下游撒谎;② 分页按逻辑单元(条目/文件/行),不按字符数;③ 诊断"agent 反复查同一主题",先怀疑工具静默截断,再怪模型行为 —— agent 不会无缘无故重复查,多半是它觉得数据缺了。

## 二、Agent 运行时(框架层的深坑)

### 故事 5:撞上递归墙,几十轮取证全部蒸发(原坑 #7)

**30 秒版**:深度调研的 8 个子 agent 几乎全部失败返回空白 —— 每个都一路探索撞上 LangGraph 的递归上限,异常硬抛,**前面几十轮工具调用收集的证据全部丢弃**。调大限制、prompt 劝它早收尾都无效(8/8 照撞)。最后发现真问题不是"它跑太多",而是"撞墙时别把工作全丢"。

**排查(关键一步是先给工具排除嫌疑)**:把三个工具单独拿出来跑 —— 返回极其精准(函数名带精确行号)。工具无辜、证据充足,问题是 reasoning 模型(deepseek-v4-pro)拿到好工具就"再看一个",**永远不会在预算内自己收尾**。顿悟在框架语义:`GraphRecursionError` 是 raise 不是软停 —— `ainvoke` 一抛什么都不返回,agent 收集的证据全在内部 state 里,调用方拿不到。所以它不是"还没总结",是"连总结的机会都没有"。加预算只是让它多撞几轮墙再丢一次。

**解法与结果**:优雅降级 —— `astream(stream_mode="values")` 流式保留最后一份 state;`except GraphRecursionError` 后把已收集证据压成文本,喂回**裸模型**(不带工具,逼它只能产文本)强制总结。冒烟测试把 limit 压到 8(约 4 轮):降级路径仍产出 8 条带真实 file:line 引用的 finding。e2e:8 个模块全走降级、0 失败,报告 80 条引用人工核验 0 幻觉。

**可迁移**:① 递归/轮次上限是硬墙,超限必须优雅降级保住已收集的工作,而不是让异常把一切带走;② 诊断"agent 失败"先直接单测工具(便宜、快),工具没问题就把锅从工具挪开;③ prompt 约束不住 reasoning 模型的探索冲动 —— 结构性降级(catch + 强制收尾)比 prompt 可靠。

### 故事 6:单测 80 个全绿,真模型 e2e 照样撞墙(原坑 #9)

**30 秒版**:给子 agent 加了轮次预算中间件,单测 80 个全绿;真模型 e2e 一跑,照样撞 `recursion_limit(44)` —— 中间件的熔断**根本没机会触发**。两层真因:计数 keying 用了对象身份(框架每个 step 新建对象 → 计数每轮清零);以及中间件的每个 hook 都是独立图节点,每轮消耗 N+2 个 superstep 而不是 2,递归墙永远抢在预算熔断之前。

**排查(两层剥离)**:
1. 第一层:预算按 `id(runtime)` 分桶,框架每 superstep 可能注入新对象 → id 每轮变 → 计数每轮清零 → 永远到不了上限。改成按 `thread_id` 分桶 —— 但 e2e 还是撞墙,说明还有第二层。
2. 写**集成探针**隔离变量:桩模型(永远吐 tool_call)+ 真 `create_agent` + 超大 recursion_limit → 干净收尾、熔断生效;调回 (max_turns+2)×2 又崩。结论:熔断机制没问题,是 recursion_limit 太低抢跑。
3. 核 `create_agent` 源码才看到:每个中间件的 before/after_model hook 都是**独立图节点**,各算 1 个 superstep(LangGraph 的 recursion_limit 按 superstep 计)。挂 5 个中间件,一轮 ReAct ≈ 7 个 superstep,不是 2 —— `44` 只够 6 轮,`max_turns=20` 永远到不了。

**根因**:①"每轮 = 2 superstep"只对裸图成立,挂中间件就是 2+N;② 单测用稳定的手工桩对象,id 不变 → 计数累积 → 绿得很虚假 —— 桩没有复刻框架的对象生命周期。

**解法与结果**:recursion_limit 按**真实中间件数动态计算**(`max_turns × (N+2) + margin`);单测加"每轮换新对象、只保持 thread_id"的回归测锁死。e2e:日志见 `Turn budget hard stop @20/20`,零撞墙,报告 267 条引用、92 条核验 0 幻觉。

**可迁移**:① 框架的计数单位要核到源码(superstep ≠ 轮;hook = 节点);② 按 run 分桶永远别用对象身份,用框架保证 run 内稳定的标识;③ "接上了但不生效"写一个几秒钟的集成探针来隔离(桩 + 真装配 + 放开限制),比烧 15 分钟真模型 e2e 便宜得多;④ 单测绿、集成红,先怀疑手工桩没复刻真实对象生命周期。

### 故事 7:「e2e 全绿、单测全崩」—— 被前序副作用掩盖的死锁(原坑 #8)

**30 秒版**:为验证故事 5 的降级逻辑直接跑单测,当场崩在 `_DeadlockError` —— 但 e2e 日志里只有递归异常、从没有死锁。同一个函数,e2e 不死锁、单测死锁。真凶:三个 @tool 函数体里的懒导入,在 LangGraph 的工具线程池里首次 import 重模块,撞上 Python 非重入的 import 锁。

**排查**:矛盾点就是线索 —— e2e 里前序的建索引节点恰好先 import 过这些模块,`sys.modules` 有缓存,工具线程只剩查表,不撞锁;单测跳过建索引直接调函数,工具线程是**首次**导入 → 包的 `__init__` 导入链在线程间争 `_ModuleLock` → 死锁。也就是说:**e2e 被前序节点的副作用恰好掩盖了一个真实存在的潜伏坑**,任何跳过前序步骤的调用方(单测、别的 workflow、临时脚本)都会踩响。

**解法**:重模块 import 全部提到模块顶层(主线程一次性载入),@tool 函数体删掉懒导入。单测不再死锁。

**可迁移**:① 被线程池调用的函数,别在函数体里懒导入重模块(asyncio `to_thread` / `run_in_executor` 同理);② "e2e 过、单测挂"是宝贵信号,先怀疑导入 / cwd / 时序差异 —— 某个前序步骤在 e2e 里顺带满足了前提,单测没那步就露馅;③ 懒导入想省的是"不调用就不载入",代价是把导入时机推到不可控的线程里 —— 对重模块不值。

## 三、架构与产品判断

### 故事 8:一套建了又拆的投票机制 ——「有 oracle 吗?」(原坑 #1)

**30 秒版**:照搬 Agentless 给补丁修复上"多候选 + 多数投票"重排,经历三次反转 —— 主路径 → 降为默认关的兜底 → 全删。砍它的那个问题成了我之后所有设计的前置检查:**这件事有 oracle 吗?样本会真多样吗?** 两个都没有,投票就是安慰剂。

**三次反转**:① 初版当主路径,还提前规划了三处复用想"摊薄设计成本";② 发现目标仓库(wpa/bluez)**没有测试套件**、模型近确定性 → N 个补丁几乎一样,投票平凡还白烧 N 倍 token —— 降成默认关的兜底;③ 深挖 Agentless 原文,它的投票是 "majority voting **after test filtering**" —— 裁判是测试;再看 2025-26 的 SOTA(OpenHands / Aider / R2E-Gym)已整体转向单轨迹 + 执行信号验证。于是"默认关的兜底"也删了 —— **死代码不是保险,是债**:留一个永不开启的开关,只增加维护面和架构噪声。单轨迹迭代 verify-refine(每次修复后执行校验再改)才是对症的路。

**可迁移**:① 上多采样/投票前先问:有廉价可靠的 oracle 吗?样本真的多样吗?两否 → 走迭代 refine;② 别留"默认关"的死代码兜底 —— 要么有用(默认开),要么删,重写比维护便宜;③ "这个原语很值钱得多处复用"是危险信号,复用是结果不是理由;④ 同名不同物要分清:补丁多数投票(已删)≠ 检索 cross-encoder 重排(标准 IR 技术,保留),砍的时候差点误伤。

### 故事 9:建到一半发现和下游 agent 重复 —— 做工具,不做平行管线(原坑 #2)

**30 秒版**:我们在委托架构里(RootRecall 调度、opencode 干重活)照搬了一套 Agentless 的分层定位漏斗放在委托之前 —— 建到一半被用户一句"opencode 本来定位就很强,这是不是冗余?"点醒:这是两个 agent 干同一件事。最终整套砍掉,换成 16 个 MCP 工具让 opencode 按需调。

**反转过程**:三轮调研坐实:① 漏斗与 opencode 的自主定位是**双重定位**;② 2026 年的主流形态就是 lead agent + 工具(连我们参考的 deer-flow 2.0 都从固定 planner 图迁到了单 SuperAgent + task 工具);③ opencode 原生支持会话中调 MCP 工具。于是定位权完全交还 opencode,RootRecall 只做它**缺的、做不便宜的**:跨会话记忆、廉价代码检索、调用链/影响面图计算、补丁验证硬门 —— 全部做成工具。原坑 #1 的教训在这里二次应验:借鉴 Agentless 之前没对齐架构形态 —— 它是**独立 agent**(自己定位自己修),我们是**委托型**,漏斗搬过来就是重复劳动。

**可迁移**:① 委托型系统建任何能力前先问:下游 agent 是不是已经会?会 → 做成工具给它调,别建平行管线;② 借方案先对齐架构形态(独立 vs 委托),同一招在不同形态里价值相反;③ 价值长在下游缺的东西上,不在下游强的东西上;④ 设计阶段被用户点醒比实现后自己发现便宜 —— 这次只建了雏形,损失可控。

### 故事 10:一条 cd 漂移,测试仓的 commit 压上了主仓 main(原坑 #21)

**30 秒版**:为跑 e2e 在 /tmp 建测试仓,某条 shell 命令的工作目录漂回了主仓 —— `git init`/`git commit`/`git checkout -b` 整串全落在主仓上:main 顶压了垃圾 commit(还夹带了两个约定永不提交的个人文件),多出一个测试分支。靠 reflog 完整恢复,并沉淀了三条至今有效的规范。

**排查**:Bash 工具的工作目录**跨调用持久** —— 前一条命令 cd 去过 /tmp,后一条建仓命令没有先核对当前位置,而 git 命令完全信任 cwd、没有任何护栏。事后 `git log` 里出现测试仓的 commit message 才暴露。好消息:reflog 证明真实历史一点没丢。

**处置(按危险度排序)**:① 先让用户拍板才在 main 上 `reset --hard`(自驱跑 e2e 的授权不延伸到重置主分支);② 删测试分支;③ 把垃圾 commit 里唯一有价值的内容(upstream-merge 的 agent 配置)干净地重新提交;④ 两个永不提交的文件恢复为 untracked。

**沉淀的规范**:① 建测试仓**全程 `git -C <路径>`**、绝不 cd —— 从机制上杜绝漂移;② 任何 `git init/commit/checkout` 前先 `pwd` 核对;③ 难以撤销的操作(reset --hard、删分支、push)永远单独向人确认,一处授权不延伸到下一处。

## 五、产品化与数据生命周期(仓库注册表时期,2026-08)

### 故事 11:补一个字段,记录被静默降级 —— 带默认值的 upsert 是坑(原坑 #22)

**30 秒版**:仓库注册表的 e2e 里,`repo gc` 点名强删返回 rc=0,worktree 却纹丝不动。排查三轮:以为 gc 逻辑坏了 → 最小复现证明 gc 无罪 → 发现是 register 补 created_at 时漏传 role,把 ephemeral 静默降级成了 unmanaged。再往下挖才知道这不是测试笔误而是 API 语义缺陷:upsert 的 role 形参带了具体默认值,任何「只想补个字段」的调用方都会触发降级 —— 而按角色分派的 gc/sync 对此零感知。

**背景**:仓库注册表(`data/repos.yaml`)用 role 驱动代码库生命周期:baseline 永久保留 + sync 定时更新,ephemeral(bug 的一次性 worktree 检出)到期由 gc 级联回收,unmanaged 一律不碰。`register()` 是 upsert 语义:未传的字段保留现值。

**排查(嫌疑三次转移)**:
1. e2e 第 ⑤ 段 `gc --name` 点名强删:rc=0、输出里连「已删」都没有,worktree 原样。第一反应 gc 的 names 过滤分支写错;翻 `gc_ephemeral` 的循环:`role != ephemeral` 直接 continue —— 看着对,但不敢只靠读码下结论。
2. 照踩坑#7 的老办法先给被怀疑的操作排除嫌疑:脱离 CLI 直接构造(bare 镜像 + add_worktree + register + 直调 gc_ephemeral)—— 删得干干净净。gc 无罪,嫌疑收窄到「进 gc 的那条记录长什么样」。
3. 打出记录:`RepoRecord(role='unmanaged')` —— 测试在 register 补 created_at 时没传 role,而 register 的 role 形参默认值是 `ROLE_UNMANAGED`,upsert 把 ephemeral 覆盖掉了。**gc 是对的,是数据被改了**。
4. 顺着再核一层:CLI 的 `--role` 也是 `default="unmanaged"` —— 用户跑 `repo register <名> --bug B-17` 只想补个 bug 号,同一条记录同样被降级。所以这不是测试笔误,是语义层的坑:带具体默认值的 upsert,让调用方无法表达「我不想改这个字段」。

**根因**:upsert 语义里「未传 = 保留现值」和「形参默认值」打架。可变的枚举/分派字段一旦有默认值,每个补字段的调用方都是降级事故的嫌疑人;而按字段分派的功能(gc/sync)对降级零感知 —— 记录还在、`repo ls` 里还看得到,只是永远不被生命周期管理,是最安静的一类失效。

**解法与结果**:语义下沉到 register 一处 —— role 形参默认改 None(None = 保留现值,新记录才落 unmanaged),CLI `--role` 的 default 同改 None 直接透传。e2e 与全量 333 个测试回绿。

**可迁移**:① upsert 的枚举/分派字段,缺省语义必须是「保留现值」(None 哨兵),别给具体默认值 —— 想给新记录兜底,在「记录不存在」分支里给;② 「操作成功、目标纹丝不动、也不报错」这类症状,先核数据侧字段再怀疑操作逻辑 —— 最小复现证明操作无罪后,嫌疑自然落到「数据被谁改过」;③ 按字段值分派的功能(角色/状态机)要把「字段被意外改写」当一类故障来防:测试里补字段是最容易踩的入口,补的时候显式带着 role 写,别赌默认值。

### 故事 12:pytest 全绿,真实数据冒烟抓到会删掉用户索引的 gc(原坑 #23)

**30 秒版**:`repo gc` 做完,333 个测试全绿;拿真实 data/ 做收尾冒烟,六个真实索引(bluez、bluez_v20、wpa…)全被标成「⚠️ 孤儿索引,要删加 --prune-orphans」。测试一个都没拦住 —— 因为测试构造的 manifest 全是新格式。真因:孤儿判定把「manifest 没有 repo_path 字段」并入「源仓已消失」的可删分支,而历史上建的所有老索引恰好都没有这个新字段。

**背景**:gc 级联回收时会顺带报告「孤儿索引」—— 没注册、且源仓已不在盘上的索引目录;默认只报告,`--prune-orphans` 才真删。判定读的是 `data/code_index/<名>/index_manifest.json` 里的 repo_path(F1 起新增的字段:建索引时记录源码仓绝对路径)。

**排查**:
1. 真 CLI 冒烟走完 register→checkout→sync→gc 全链,收尾顺手对真实 data/ 跑了把纯报告的 `repo gc` —— 输出把 bluez、bluez_v20、wpa 等六个索引全列入「孤儿」。可它们的源仓(code-test/ 下两版 bluez)明明在盘上。
2. 翻 manifest 才看到:这批索引是 F1 之前建的,清单里根本没有 repo_path;而判定写的是 `rp is None or not Path(rp).is_dir()` —— 「没有字段」和「字段指向的路径没了」被并进了同一个可删分支。
3. 为什么 333 个测试全绿:e2e 里构造的 manifest 全是新代码写的、天然带 repo_path —— 「老格式」这种形态在合成数据里天然缺席。测试验证的是新代码对新数据,升级兼容性只有真实数据考得到。

**根因**:两个字段语义被混为一谈 —— 「缺字段」是升级常态(老数据 + 新 schema 的组合永远存在),「字段判定失败」才是可删证据;清理类功能把前者并入后者,等于把全部历史数据判了死刑,再配一个 `--prune-orphans` 就是给用户递刀。

**解法与结果**:判定拆三分支 —— 记了 repo_path 且路径消失 → 孤儿(可删);没有 repo_path → 单列 legacy 只提示,并给迁移路径(对源仓重跑一次 index,manifest 即记 repo_path 纳入管理);manifest 损坏 → 同 legacy 不删。e2e 补断言(legacy 不受 --prune-orphans 影响),真实 data/ 复跑,六个索引全部变成 ℹ️ 未登记提示。

**可迁移**:① 清理/删除类功能里,「字段缺失」必须与「字段判定失败」分开处理 —— 老数据缺新字段是常态不是罪,判它死刑前先问「这个字段是什么时候才有的」;② 合成数据的测试永远构造不出「历史格式」,带删除能力的功能上线前,拿真实数据 dry-run 一遍 —— 这一把冒烟比全部 333 个测试更能暴露兼容问题;③ 报告的措辞就是接口:「可删」和「未登记、重跑即纳入管理」必须是两种不同提示,别让用户顺着一条提示走到底把该留的删了。

### 故事 13:功能清单样样能接,用户旅程条条断链 —— 三个期望逼出的产品化转向(原坑 #27)

**30 秒版**:用户提了三个期望:① git clone 后一条脚本装好;② 在 bug 目录里问一句「结合问题描述 txt、bluez 5.50.61 代码和 bug 日志,分析 bug 根因」就能开干;③ 基线仓永久保留、定时同步上游并分析,bug 临时仓分析完即删。拿功能清单自检,16 工具 + 8 skill 样样接得住;把三个期望各当一条用户旅程从零走一遍 —— 条条断链。核心转向:**三条断链没有一条能靠「再加一个分析工具」修好**,部署面/交互面/数据面各断各的,得各开各的药(落成 F1–F5)。这轮对照发生在动手之前,故事 11/12 是随后落地时的两个坑。

**背景**:项目当时的心智停在工具箱阶段 —— 能力=工具数,工具够强,剩下的 agent 自己想办法、用户自己想办法。而这三个期望没有一个落在功能面上:它们考的是「用户从 clone 到问出第一个问题」这段路上,系统替他挡了几步。

**排查(三条旅程走查,数手工步)**:
1. **期望①(装得轻)**:clone 后要装依赖、建索引、配 MCP、挂 skill、写 AGENTS.md 路由 —— 五步手工、步步能配错(opencode 还有全局/项目两层配置要选对,`{env:}` 不展开的坑在前头等着)。
2. **期望②(一句话开问)**:这句话要成立,agent 先得答两问:这是哪类事(→ 路由到 bug-rca)?「bluez 5.50.61」在哪(→ 解析成仓库路径)?当时两问皆无解 —— 路由表不存在;名称解析也干脆不存在,compare SKILL 原文教的是「**直接问用户要仓库绝对路径**」。用户嘴里永远是「项目名 + 版本」,工具链要的却是绝对路径,中间缺一整层。
3. **期望③(多库生命周期)**:clone 进 data/repos 的仓无人登记、无角色,sync / 上游分析无从挂起;workspace 攒到 991MB 没有任何回收机制;**索引名、仓库路径、clone 落点、清理是四条互不知晓的链** —— 索引清单不记 repo_path、resolver 的可用 remote 是空的、SKILL 教你问用户、gc 不存在。每条链局部都「能用」,拼起来没人负责。

**根因**:三个期望分属三个「面」—— 部署面(到达成本)、交互面(入口收敛)、数据面(资产生命周期);而项目此前的迭代单位只有「功能面」。拿**功能清单**对照期望,会得出「都能接住」的错觉;拿**用户旅程**对照,才看得见断链。四条断链共一个病灶:**仓库这个实体被四个子系统各自引用,却没有一个共享的登记处**。

**解法与结果**:先立登记处、再把各条链挂上去 —— F1 仓库注册表(name↔path↔role↔bug_id)作唯一接合点 + 名称解析四级链(本地路径→注册表→索引 manifest→clone 目录),把「问用户」压成最后兜底;F2 `install --global` / `here` 一条命令收敛五步手工(幂等,永不覆盖用户已有配置);F3 bare mirror + worktree + 三角色(baseline 永久 / ephemeral 到期 gc 级联回收 / unmanaged 一律不碰);F4 `repo sync --analyze` 纯 git 三态对上游出报告(只报告不合入);F5 索引 `--seed` 播基线、只重嵌改动文件。333 测试全绿 + 真实 data/ 冒烟收尾。**验收标准同步上移:真 e2e 不是 pytest 数,是「空 bug 目录 + 一句自然语言 → 出根因卡」** —— 后续 P0 的 find_repo / 自动开仓,就是这条验收倒逼出来的。

**可迁移**:① **功能清单对照 ≠ 可用性验收** —— 每个产品期望都当一条用户旅程从零走一遍、数手工步数;「工具在」和「用户到得了工具」是两个指标。② **先分面再开药**:部署/交互/数据面的病,加功能面(工具)的药医不好;判断一个需求属于哪个面,看它的修复动不动「用户操作路径」和「数据归属」,而不是「分析能力」。③ **多个子系统共享同一实体却没有登记处时,别在各子系统里打补丁** —— 先立登记处、各链挂上去,四条断链共用一把钥匙。④ **skill 文档里每一句「问用户要 X」都是交互面的反向补丁** —— 写 skill 时省下的事,变成用户每一次多费的步数;名称解析链的目标就是把这句压到最少。⑤ **验收标准要长在期望原文上**(「一句话开问」的验收就是那一句话),不是长在实现物上(pytest 数)。

## 短篇

### 短篇 A:backlog 点名的文件是红鲱鱼(原坑 #6)

修"超长 chunk 无上限":backlog 说肇事者是某两个文件、根因在"符号路径";照单修完、拿点名文件验证(max 12275,没超)以为成了。**全仓聚合统计**一扫才见真凶:真正的肇事头文件 304044 字符、整个文件没有一个被解析的符号(C 头文件常态),走的是另一条**同样没有上限**的模块兜底路径。教训:① 修"无上限"类 bug,要把所有产该产物的路径都过一遍,不只被点名那条;② 离线验证用全仓聚合统计(max / 超限计数),别验点名样本 —— 红鲱鱼样本会让你误判已修,而全仓扫一眼只要几秒。

### 短篇 B:评审草稿说「没人调用」,grep 一查全在(原坑 #20)

一份架构评审草稿提了 4 条改进,落地时逐条实证:**没有一条照草稿原样实现是对的**。两条的"短板"是误判 —— 草稿说"巩固函数无人调用",实际 CLI 早就接了命令、检索早就计数;草稿说"不二次压缩是短板",对标实现(deer-flow 生产级)也不二次压 —— 对标做了的才可能是待补,对标也没做的大概率是 YAGNI。还有一条藏着度量陷阱:换 sqlite-vec 做向量检索,它**默认距离是 L2 不是 cosine**,不显式指定就静默把相似度排序搞错、还不报错。教训:① 草稿/读码印象 ≠ 实证,每条判断落地前 grep 调用点、读对标实现、跑最小探针;② 区分"现象"和"短板",别把"缺一个触发点"夸大成"整个功能没人用";③ 换库先核默认行为(度量/空值/batch),默认值常与你的语义相悖。

### 短篇 C:换一套环境,三条虫当场现形 —— 干净机演练(原坑 #30/#31 + 服务 PATH)

**30 秒版**:发布前在 /tmp fresh clone 模拟"同事的机器"跑一遍装机脚本,一次演练连抓三条虫 —— 而且事后复盘,三条在开发机上**永远测不出来**:零 key 提示文案里的 Markdown 反引号在双引号 echo 里是命令替换,没配 key 的机器跑装机脚本会静默拉起 800MB torch 卡死(开发机一直配着 key,这条分支从没走过);换目录重装时 mcp 块换到新根、8 个 skill 软链还吃着旧根,旧根一删全断(开发机从不换目录);systemd user 服务是极简 PATH,uv 和 opencode 都看不见,timer 里的同步直接起不来(交互 shell 的 PATH 是 profile/nvm 喂的,服务环境是裸的)。

**方法论**:① 你测不出的 bug,藏在"你和用户的环境差异"里 —— 测试矩阵要主动包含你自己**永远不处于**的形态:没配 key 的机器、换了目录的重装、没有终端的服务环境;② 装机脚本 / 部署单元的验收标准不是"在我机器上跑通",是"在一台什么都没有的机器上跑通" —— fresh clone 到 /tmp 十分钟一轮,是性价比最高的一类测试;③ 根因层的通用课:**给用户看的技术文案也是代码**(它活在 shell 里),"在我这儿没触发"不等于无害;④ #34→#36 是同一病灶的三个入口(交互终端手动配、systemd 服务 PATH、multica daemon env)—— 每新增一个「拉起 agent 的宿主」,「宿主环境 ≃ 我的 shell」这个隐式假设就再破一次;接新宿主先列 env 差异清单,再跑真任务。
